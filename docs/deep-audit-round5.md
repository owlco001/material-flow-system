# 第五轮：机台页响应隔离与任务、工时完整性

基线32fa40b；工作分支fix-deep-audit-138ff95。只改Android，本轮不推送、不部署、不发布APK。后端保留0.22.3，Android版本0.5.56 / 63。

## 修复目标

1. 旧机台详情或聚合响应不得覆盖当前机台，也不得在登出、新登录、角色预览或离开页面后重新填充页面。
2. 机台任务与工时读取完整分页；任务/人员不能仅看前20条，工时卡不能把前20组(task,assembler)加总冒充全部。
3. 异常页、失败后续页和可检测的总数变化不得静默发布部分总量。

## 方案与兼容性

机台详情和聚合属于同一个operationScope子job，并持有session和device request generation。每次网络等待后、后续请求前和最终写回前校验所属会话与请求。取消旧job节约可取消请求资源，世代校验处理不配合取消的迟到回调。新登录、登出、401失效、角色预览进出清空机台内容；导航及直接打开订单/扫码等入口失效旧机台任务。

保留现有每页20条、原角色/机台筛选和后端归属口径。任务按task id合并；工时按(taskId,assemblerId)合并，逐页读取服务端事实后再供现有卡片求和。旧labor服务端缺total时继续读取至短页；分页不推进、元数据异常或后续页失败时，该分区不显示部分结果并给出“读取不完整”提示，其他成功分区仍可展示。不修改后端分页API的totalLaborMinutes字段含义。

依赖仅新增测试用kotlinx-coroutines-test 1.8.1（与已有显式coroutines-guava依赖版本一致），用于控制Dispatchers.Main。生产APK不新增运行时依赖。

## 证据与验收

最初8项可控回归在原32fa40b实现全部失败，修复后转绿。测试使用Deferred及刻意不响应取消的continuation，区分“取消碰巧成功”与真正阻止旧状态写回。覆盖A/B切换、同机台重复刷新、登出后重登、预览、导航离开、0/20/21/41组数据与未知total回退。

独立复核补充：直接打开订单不经过navigate也必须失效旧机台请求；OFFSET跨页过程中总数降低不得被当作提前正常结束。对应三项回归先红后修复。复核另指出后台订单缓存刷新不应取消当前机台聚合；单项红测后分离显式导航与后台刷新，订单不在前台时仅更新自身缓存，不写当前页面。最终Android完整285项/52类，0失败/错误/跳过；新机台专项20项全绿，testDebugUnitTest与assembleDebug成功（最后一轮55秒）。本轮后端无源码变化，相关装配列表、工时归属与机台物料契约11项复验通过；598项全量是第四轮已通过基线，本轮没有重跑后端全量。Room实际生成SQL、图标75文件、全部ratchet、YAML与diff格式检查通过。

可确定的改善：21组工时每组10分钟应显示210分钟（旧实现只显示200）；41组应显示410分钟（旧实现仍只显示200）。这是完整性修复，不以额外HTTP读取声称速度提升。页间没有数据库快照/游标，固定数量和不推进检查只能发现部分变化，不承诺跨HTTP多页的事务快照一致性。
