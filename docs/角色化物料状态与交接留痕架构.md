# 角色化物料状态与交接留痕架构

## 1. 目标与范围

本迭代将登录后的首页与订单详情改为按服务端角色呈现业务信息，并为每一次物料交接建立不可抵赖的审计留痕。

- 操作员：优先查看“是否已到工位/已领取”；仅展示本人负责订单、机台和物料状态。
- 物料员：优先查看“是否已出库/待出库”，执行领料、出库交接发起。
- 仓库管理员：优先查看待审核、待出库、待交接和异常；执行出库确认、交接确认和审批。
- 管理员：在仓库管理员能力之上查看全量状态、用户和审计记录。
- 业务边界：仅厂内物料，不引入外部物流、承运商、线边库或配送工位。

服务端角色是唯一权限来源；客户端只负责展示收敛，不能通过隐藏按钮代替鉴权。

## 2. 模块图（文字版）

```text
[LoginScreen]
    │ 登录成功 + access/refresh token + UserRole
    ▼
[SessionStore(EncryptedSharedPreferences)] ──冷启动恢复──> [AuthSession]
    │
    ▼
[RoleWorkspaceRouter]
    ├── OPERATOR ───────> [OperatorDashboard]
    ├── MATERIAL ───────> [MaterialDashboard]
    ├── WAREHOUSE_ADMIN -> [WarehouseDashboard]
    └── ADMIN ──────────> [AdminDashboard]
             │                         │
             ▼                         ▼
[OrderMaterialQuery]            [HandoverWorkflow]
             │                         │
             └──────────────┬──────────┘
                            ▼
                 [MaterialStatusTimeline]
                            │
                            ▼
              [AuditLog / HandoverEvidence]
                            │
                            ▼
        [API: role-summary / handovers / audit-events]
                            │
                            ▼
 [FastAPI Service] -> [SQLite/PostgreSQL] -> [transaction + idempotency]
```

依赖方向固定为：UI → ViewModel → Repository → API/本地存储；UI 不直接访问数据库或拼接权限请求。

## 3. 角色展示规则

服务端返回 `role` 后，客户端使用以下固定映射：

- `OPERATOR`：默认工作台显示订单/机台/物料的 `ARRIVED`、`PICKED_UP`、`AT_STATION`；主操作为确认领取。
- `MATERIAL`：默认工作台显示 `OUT_OF_STOCK`、`ARRIVED`、`PICKED_UP`，并突出 `OUTBOUND_PENDING`；主操作为发起出库交接。
- `WAREHOUSE_ADMIN`：默认显示待审批、待出库和待交接列表；主操作为审核/确认。
- `ADMIN`：显示全角色汇总、异常和审计入口。

核心状态必须由服务端返回 `statusCode/label/colorToken`，客户端不得仅根据数量自行推导“已领取”或“已到工位”。

## 4. 接口定义（函数签名级）

### 4.1 Android 数据结构与接口

```kotlin
enum class UserRole { OPERATOR, MATERIAL, WAREHOUSE_ADMIN, ADMIN }

enum class HandoverStatus { PENDING, CONFIRMED, REJECTED, CANCELLED }

data class RoleSummary(
    val role: UserRole,
    val pendingApprovalCount: Int,
    val pendingOutboundCount: Int,
    val pendingHandoverCount: Int,
    val atStationCount: Int,
    val pickedUpCount: Int,
    val outOfStockCount: Int,
    val generatedAt: String
)

data class MaterialWorkItem(
    val id: String,
    val orderNo: String,
    val deviceId: String,
    val deviceType: String,
    val deviceNo: String,
    val materialId: String,
    val materialCode: String,
    val materialName: String,
    val requiredQuantity: Int,
    val issuedQuantity: Int,
    val pickedQuantity: Int,
    val statusCode: String,
    val statusLabel: String,
    val colorToken: String,
    val lastHandoverId: String?
)

data class HandoverRecord(
    val id: String,
    val orderNo: String,
    val deviceId: String,
    val materialId: String,
    val quantity: Int,
    val fromLocation: String,
    val toTarget: String,
    val handoverStatus: HandoverStatus,
    val senderUserId: String,
    val senderName: String,
    val receiverUserId: String?,
    val receiverName: String?,
    val initiatedAt: String,
    val confirmedAt: String?,
    val remark: String?
)

interface RoleWorkspaceRepository {
    suspend fun loadRoleSummary(): Result<RoleSummary>
    suspend fun listWorkItems(status: String?, orderNo: String?, page: Int, pageSize: Int): Result<List<MaterialWorkItem>>
    suspend fun createHandover(request: CreateHandoverRequest): Result<HandoverRecord>
    suspend fun confirmHandover(handoverId: String, requestId: String): Result<HandoverRecord>
    suspend fun rejectHandover(handoverId: String, reason: String, requestId: String): Result<HandoverRecord>
    suspend fun listHandoverTimeline(materialItemId: String, page: Int, pageSize: Int): Result<List<HandoverRecord>>
}

data class CreateHandoverRequest(
    val workItemId: String,
    val quantity: Int,
    val fromLocation: String,
    val toTarget: String,
    val receiverUserId: String?,
    val remark: String?,
    val clientOperationId: String
)
```

### 4.2 REST API

`GET /api/v1/workspace/summary`

- Header：`Authorization: Bearer <accessToken>`、`X-Request-Id`
- 返回：`RoleSummary` JSON；服务端依据 token 角色过滤统计范围。

`GET /api/v1/workspace/material-items?status={status}&orderNo={orderNo}&page={page}&pageSize={pageSize}`

- `page` 从 1 开始，`pageSize` 取 20，最大 50。
- 返回：`{items: MaterialWorkItem[], page: Int, pageSize: Int, total: Int}`。

`POST /api/v1/handovers`

```json
{
  "workItemId": "string",
  "quantity": 1,
  "fromLocation": "WH-A-01",
  "toTarget": "device:xxx",
  "receiverUserId": "string|null",
  "remark": "string|null",
  "clientOperationId": "uuid"
}
```

- Header 必须包含 `Authorization`、`Idempotency-Key=clientOperationId`、`X-Request-Id`。
- 操作员只能确认领取；物料员只能发起出库交接；仓库管理员/管理员可确认或驳回。
- 数量必须为正整数；库存、物料状态和交接记录在同一事务内变更。
- 成功：`201` 返回 `HandoverRecord`；重复幂等键返回同一业务结果。

`POST /api/v1/handovers/{handoverId}/confirm`

- 请求体：`{"requestId":"uuid"}`。
- 成功：`200`；已确认、无权限、状态冲突分别返回 `409/403/409`。

`POST /api/v1/handovers/{handoverId}/reject`

- 请求体：`{"reason":"string","requestId":"uuid"}`；`reason` 长度 1~500。
- 成功：`200`，状态变为 `REJECTED`。

`GET /api/v1/handovers/{workItemId}/timeline?page=1&pageSize=20`

- 返回按服务端时间倒序的交接记录；仅返回当前用户有权限查看的数据。

所有错误统一返回 `{error:{code,message,retryable,traceId}}`。

## 5. 数据结构定义

### 5.1 `material_work_items`

- `id TEXT PRIMARY KEY`
- `order_no TEXT NOT NULL`
- `device_id TEXT NOT NULL`
- `device_type TEXT NOT NULL`
- `device_no TEXT NOT NULL`
- `material_id TEXT NOT NULL`
- `required_quantity INTEGER NOT NULL CHECK(required_quantity > 0)`
- `issued_quantity INTEGER NOT NULL DEFAULT 0 CHECK(issued_quantity >= 0)`
- `picked_quantity INTEGER NOT NULL DEFAULT 0 CHECK(picked_quantity >= 0)`
- `status_code TEXT NOT NULL`
- `version INTEGER NOT NULL DEFAULT 1`
- `created_at TEXT NOT NULL`
- `updated_at TEXT NOT NULL`

唯一约束：`(order_no, device_id, material_id)`。

### 5.2 `material_handovers`

- `id TEXT PRIMARY KEY`
- `work_item_id TEXT NOT NULL REFERENCES material_work_items(id)`
- `quantity INTEGER NOT NULL CHECK(quantity > 0)`
- `from_location TEXT NOT NULL`
- `to_target TEXT NOT NULL`
- `status TEXT NOT NULL CHECK(status IN ('PENDING','CONFIRMED','REJECTED','CANCELLED'))`
- `sender_user_id TEXT NOT NULL`
- `receiver_user_id TEXT NULL`
- `remark TEXT NULL`
- `client_operation_id TEXT NOT NULL UNIQUE`
- `request_id TEXT NOT NULL`
- `initiated_at TEXT NOT NULL`
- `confirmed_at TEXT NULL`
- `rejected_at TEXT NULL`
- `reject_reason TEXT NULL`

### 5.3 `audit_events`

- `id TEXT PRIMARY KEY`
- `event_type TEXT NOT NULL`
- `entity_type TEXT NOT NULL`
- `entity_id TEXT NOT NULL`
- `actor_user_id TEXT NOT NULL`
- `actor_role TEXT NOT NULL`
- `request_id TEXT NOT NULL`
- `client_operation_id TEXT NULL`
- `before_json TEXT NULL`
- `after_json TEXT NULL`
- `server_time TEXT NOT NULL`
- `device_id TEXT NOT NULL`

审计事件只追加不更新：`HANDOVER_CREATED`、`HANDOVER_CONFIRMED`、`HANDOVER_REJECTED`、`MATERIAL_PICKED_UP`、`MATERIAL_AT_STATION`、`OUTBOUND_CONFIRMED`。

## 6. 技术选型及理由

- Android：现有 Jetpack Compose + ViewModel + Repository，保持现有工程，减少迁移风险。
- 会话：EncryptedSharedPreferences 保存 access/refresh token；不保存密码。冷启动先恢复 token，再由服务端请求验证。
- API：沿用现有 HttpURLConnection/JSON 客户端，契约稳定后可无痛替换 OkHttp；本轮不增加网络依赖。
- 服务端：沿用 FastAPI；交接确认、库存变更、状态更新、审计写入使用单事务。
- 数据库：当前 SQLite 兼容约束与索引；生产并发提高时迁移 PostgreSQL，接口不变。
- 离线：交接创建允许进入现有离线队列，但必须携带 `clientOperationId` 和版本号；确认动作默认在线，避免离线重复确认。
- 8GB 中端 Android：工作台只加载 20 条、交接时间线只加载 20 条；禁止一次拉取全订单/全审计，单次同步并发不超过 2。

## 7. 验收标准

1. 四种角色登录后进入不同工作台，服务端越权请求返回 `403`。
2. 操作员能看到物料“已领取/已到工位”状态及最后一次交接时间。
3. 物料员和仓管能看到“已出库/待出库”状态及责任人。
4. 发起、确认、驳回交接均生成审计事件，包含用户、角色、设备、服务端时间和 requestId。
5. 同一 `clientOperationId` 重试不重复扣库存、不重复生成交接记录。
6. 库存不足、版本冲突、状态非法时事务整体回滚。
7. 冷启动恢复会话后 UI 与服务端角色一致；退出登录清除 token 和本地用户缓存。
8. 在 8GB 中端 Android 上工作台首屏不加载全量数据，列表分页可用。
