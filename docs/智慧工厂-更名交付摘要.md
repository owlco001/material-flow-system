## 五、测试结果（含一个必须澄清的结论）

### Android：编译通过；单元测试存在**基线既有**的顺序依赖

编译 `BUILD SUCCESSFUL`。混跑 `LogisticsViewModel*` 时约 50% 概率失败：

```
LogisticsViewModelUserManagementTest > deleteUserExposesLoadingThenSuccessAndRefreshesList FAILED
LogisticsViewModelAssemblyTest > removingAssemblyMemberUpdatesTaskAndReportsConflict FAILED
LogisticsViewModelAssemblyTest > assignmentFailureClearsLoadingAndExposesRetryMessage FAILED
```

**根因**：所有测试类都这样构造被测对象——

```kotlin
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Unconfined)
val viewModel = LogisticsViewModel(repository, scope)  // init 内启动会话恢复协程
viewModel.login(...)                                    // 未等待恢复协程结束
```

`Dispatchers.Unconfined` 让协程立即执行至首个挂起点，fake repository 又全是同步返回，恢复协程于是**一路跑完**并把 `authState` 写成 `Unauthenticated`。若它落在 `login()` **之后**落地，就覆盖了刚写入的 ADMIN 登录态，使角色守卫 `if (role != ADMIN) return` 直接返回、断言失败。

**证据链（决定性）**：

| 运行方式 | 结果 |
|----------|------|
| **纯基线 `171a0de`，改动全部 stash，多类混跑 3 轮** | **FAILED / SUCCESSFUL / FAILED** |
| 单类 `*LogisticsViewModelUserManagementTest*` | 5/5 通过 |
| 单类 `*LogisticsViewModelAssemblyTest*` | 通过 |
| 仅加两条**未使用的 import**（零逻辑改动） | 可复现失败 |

**结论**：测试自身对 `Dispatchers.Unconfined` 调度顺序的依赖，**基线原生存在**，非本次更名引入。

> 排查中我曾误判为「改动引入的竞态」，并做了两次未成功的「修复」。经基线 A/B 对照（stash 掉全部改动后同样失败）**证伪并已撤回**，相关改动与临时诊断代码均已从代码库清除。**未修复，如实记录。**
