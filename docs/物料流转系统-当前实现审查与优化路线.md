目标：

```text
QUEUED → SYNCING → SUCCEEDED
                 ├→ RETRY_WAIT（网络/5xx）
                 ├→ CONFLICT（409）
                 └→ FAILED（不可重试）
```

固定参数：

- 每批最多 20 条。
- 并发最多 2。
- 自动重试最多 5 次。
- `clientOperationId` 重试不变。
- 409 进入 `CONFLICT`，不得自动改写 payload。
- payload 使用 Android Keystore 派生密钥加密。
- Worker 使用网络约束，进程被杀后可从 Room 恢复。

## 5. 技术选型及理由

- Android 网络层：优先 Retrofit + OkHttp，减少手写 HTTP 状态和 JSON 解析错误；使用统一错误 DTO 保留 `code/retryable/traceId`。
- Android 序列化：kotlinx.serialization，DTO 与 JSON 字段显式绑定。
- 离线数据库：Room，采用迁移而不是破坏性重建；payload 使用 Keystore 加密后再落库。
- 调度：WorkManager，使用网络约束、唯一工作名和指数退避；业务幂等由服务端最终保证。
- 后端 API：FastAPI + Pydantic，写接口禁止裸 `dict`；保留 SQLite WAL 作为开发/测试实现，生产切换 PostgreSQL。
- 部署：systemd + Uvicorn + Nginx；生产必须 HTTPS，测试 HTTP 仅限受控网络。
- 测试：后端 pytest；Android JVM/Compose 契约测试；MockWebServer；真机专项测试单独记录，不以编译替代。

## 6.1 可直接开发的数据结构定义

### 6.1.1 调拨机台—工时联动（新增需求）

当前实现仅在 `temporary_transfers.source_task_id` 保存可选装配任务，`labor_records.task_id` 对临时调拨为空，导致临时调拨工时无法稳定归属到机台；本节冻结为下一开发切片。临时调拨不并入原装配工时，但必须归属一个机台，并可按机台、订单和人员追溯。

文字模块图：

```text
装配任务 assembly_tasks
  └─ device_id/device_no + order_no
       ↓ 1:N
临时调拨 temporary_transfers
  └─ source_task_id + device_id/device_no（快照）
       ↓ 1:1
工时 labor_records(type=TEMPORARY_TRANSFER)
       ↓ 聚合
机台工时 / 订单工时 / 车间总工时
```

后端接口签名（必须保持现有路径兼容）：

```python
POST /api/v1/assembly/temporary-transfers/start(
    body: TemporaryTransferStartRequest,
    request: Request,
    user: CurrentUser,
    idempotency_key: UUID = Header(..., alias="Idempotency-Key"),
) -> TemporaryTransferStartResponse

POST /api/v1/assembly/temporary-transfers/{transfer_id}/complete(
    transfer_id: str,
    body: TemporaryTransferCompleteRequest,
    request: Request,
    user: CurrentUser,
    idempotency_key: UUID = Header(..., alias="Idempotency-Key"),
) -> TemporaryTransferCompleteResponse

GET /api/v1/workshop/machine-progress(
    page: int = Query(1, ge=1),
    page_size: int = Query(20, ge=1, le=100, alias="pageSize"),
    device_id: str | None = Query(None, alias="deviceId"),
    user: CurrentUser,
) -> MachineProgressPageResponse
```

请求/响应数据结构：

```python
class TemporaryTransferStartRequest(BaseModel):
    task_id: str = Field(min_length=1, alias="taskId")
    device_id: str = Field(min_length=1, alias="deviceId")
    remark: str = Field(min_length=1, max_length=500)
    client_operation_id: UUID = Field(alias="clientOperationId")

    client_operation_id: UUID = Field(alias="clientOperationId")

class TemporaryTransferStartResponse(BaseModel):
    temporary_transfer_id: str = Field(alias="temporaryTransferId")
    labor_record_id: str = Field(alias="laborRecordId")

    order_no: str = Field(alias="orderNo")
    device_id: str = Field(alias="deviceId")

class TemporaryTransferCompleteResponse(BaseModel):

    status: Literal["COMPLETED"]

    completed_task_count: int = Field(ge=0, alias="completedTaskCount")
    progress_percent: int = Field(ge=0, le=100, alias="progressPercent")

```

实现约束：

- `taskId` 必填，且任务必须属于当前装配工；`deviceId` 必须与任务的 `device_id` 精确一致，否则返回 `409 DEVICE_TASK_MISMATCH`。
- 服务端从 `assembly_tasks` 读取并固化 `order_no/device_id/device_no` 快照，客户端不得自行拼接订单或机台归属。
- `labor_records.task_id`、`temporary_transfers.source_task_id` 均指向该任务；临时调拨记录的 `type` 固定为 `TEMPORARY_TRANSFER`。
- 开始调拨时暂停当前装配工时；完成调拨时只结束临时调拨工时，不自动完成装配任务；装配工恢复后继续原任务。
- 机台统计分别返回 `ASSEMBLY`、`TEMPORARY_TRANSFER` 和总工时；未完成的 ACTIVE 工时按服务端当前时间计算展示值，但数据库 `duration_minutes` 只在完成时固化。
- 同一 `clientOperationId` 必须返回原响应；同一幂等键不同 payload 返回 `409 IDEMPOTENCY_CONFLICT`；所有动作写入 requestId、deviceId、操作者和前后状态审计。

技术选型及理由：沿用 SQLite WAL + FastAPI/Pydantic，避免本切片引入新服务；使用机台快照字段抵御任务后续变更，使用 SQL 聚合保证订单/机台/车间口径一致，Android 仅展示服务端汇总，避免移动端计算工时产生时钟和并发偏差。

### 离线操作

```kotlin
enum class SyncStatus { QUEUED, SYNCING, SUCCEEDED, RETRY_WAIT, CONFLICT, FAILED }

data class OfflineOperation(
    val id: Long,
    val clientOperationId: String, // UUID，唯一且重试期间不变
    val operationType: String,
    val encryptedPayload: String,
    val status: SyncStatus,
    val retryCount: Int,
    val errorCode: String?,
    val createdAtEpochMs: Long,
    val updatedAtEpochMs: Long

```

不允许将密码、access token、refresh token 或完整请求头写入 `encryptedPayload`；payload 只保存业务请求所需字段。

## 6.2 精确接口与函数签名

### Android 离线同步

```kotlin
interface OfflineOperationDao {
    suspend fun insert(operation: OfflineOperation): Long
    suspend fun claimBatch(limit: Int = 20): List<OfflineOperation>
    suspend fun updateStatus(id: Long, status: SyncStatus, errorCode: String?, now: Long)
    suspend fun countByStatus(status: SyncStatus): Int
}

class OfflineSyncScheduler(context: Context) {
    fun enqueue(): Operation
}

class OfflineSyncWorker(appContext: Context, params: WorkerParameters) : CoroutineWorker(appContext, params) {
    override suspend fun doWork(): Result
}
```

约束：`claimBatch` 不得超过 20 条；调度使用固定唯一工作名和 `KEEP`；网络/5xx 未超过 5 次时返回 `Result.retry()`；409 更新为 `CONFLICT` 并返回成功，避免无限重试。

## 7. 风险与打回项

以下事项在修复前不能标记为完整 V1：

1. 后端继续返回契约外 `MACHINE` 或接受旧 `ORDER_NO`。
2. 写接口继续使用裸 `dict` 或缺少幂等/请求 ID。
3. 以 JVM 构建成功宣称 WorkManager 离线能力已完成真机验收。
4. 以 APK 构建成功宣称真机扫码和断网恢复通过。
5. 以 SQLite 测试部署宣称生产数据库部署完成。
6. 在现有已初始化 VPS 上隐式重置管理员密码或破坏 setup 状态。
