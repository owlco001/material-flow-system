## 为什么有东西没改（重要）

以下三处**故意保留**原样，不是遗漏：

### 1. Android 包名 `com.company.logistics`

改包名等同于发布一个**全新的 App**：已安装旧版本的设备不会覆盖升级，而是并排出现两个图标，旧包的登录态与离线队列数据无法继承。车间设备现场会出现「两个博阳智造」。

当前取舍：**保留 `logistics` 包名**，换取已装机器可平滑升级。若将来确实需要更换，必须配套：卸载指引 + 数据迁移 + 版本共存期。

### 2. 后端数据路径与环境变量

`MATERIAL_FLOW_DATA`、`/srv/material-flow/data`、`material_flow.db`、`SERVICE_NAME=material-flow` 全部**保持不变**。

这些指向服务器上的**生产数据库与上传目录**。改名而不做迁移脚本，服务重启后会找不到库并新建空库——历史库存、审计记录在界面上看起来就像「全部丢失」。

当前取舍：**只改对外名称，不动数据路径**。参见 `material-flow-backend/app/main.py` 第 28–32 行。

验证结果：加载后 `title=智慧工厂 API`，路由数 66，`DB_PATH=/srv/material-flow/data/material_flow.db`，`SERVICE_NAME=material-flow` —— 三者均未变。

### 3. 文档文件名与指向它们的引用

`docs/` 与 `tasks/` 下的文件名保持不变（如 `物料流转系统-V1-API契约冻结补遗.md`）。因此代码与文档中引用这些文件名的位置（`Models.kt`、`main.py`、`test_contract_acceptance.py`）也**必须保留原名**，否则引用会失效。

正文替换脚本对**反引号包裹的路径引用**做了保护，只改正文产品名、不动路径字面量。

## 测试验证与一个必须澄清的结论

### Android 单元测试存在**基线既有的**顺序依赖，与本次更名无关

`LogisticsViewModel*` 系列测试存在跨测试类的执行顺序依赖，表现为间歇性失败（约 50% 概率）：

```
LogisticsViewModelUserManagementTest > deleteUserExposesLoadingThenSuccessAndRefreshesList FAILED
LogisticsViewModelAssemblyTest > removingAssemblyMemberUpdatesTaskAndReportsConflict FAILED
LogisticsViewModelAssemblyTest > assignmentFailureClearsLoadingAndExposesRetryMessage FAILED
```

**根因**（经独立实测修正，早前「恢复协程覆盖登录态」的说法已证伪）：

测试类只覆写了 `login()` / `workspaceSummary()`，**未覆写 `workspaceMaterialItems()`**。于是 `login()` 成功后的工作台加载回落到**真实的 `MaterialFlowApi` 网络调用**（跑在 `Dispatchers.IO` 上），该调用失败触发 `expireSession()`，把 `authState` 异步重置为 `Unauthenticated` —— 后续带角色守卫的方法（`deleteManagedUser`、`assignAssemblyMembers`、`removeAssemblyMember`）在守卫处提前 `return`，断言拿到 `null`。

重置发生在 IO 线程上，**落地时机不确定**：落在断言前还是后决定了成败，这才是间歇性的来源。

**强相关佐证**：未覆写 `workspaceMaterialItems` 的类 = `AssemblyTest`、`UserManagementTest`（均为 ADMIN 用例）→ **恰是失败清单**；已覆写的类（`AdminRolePreview` / `ApprovalAudit` / `Handover` / `Workspace`）→ **从不失败**。

**证据链**：

| 运行方式 | 结果 |
|----------|------|
| 纯基线 `171a0de`，多类混跑 3 轮 | **FAILED / SUCCESSFUL / FAILED**（2/3 失败） |
| 单类运行 `*LogisticsViewModelUserManagementTest*` | 5/5 通过 |
| 单类运行 `*LogisticsViewModelAssemblyTest*` | 通过 |
| 仅添加两条**未使用的 import**（零逻辑改动） | 可复现失败 |
| 探针驱动真实 ViewModel | 构造后 `Unauthenticated` → `login` 后 `Authenticated(ADMIN)` → 1.5 秒后 `Unauthenticated/role=OPERATOR` |
| 等价复现「恢复协程覆盖」假设 20 万次 | `mismatch=0`（**证伪**该假设） |

**结论**：这是**基线原生存在**的问题，并非更名引入。排查中一度误判为「改动引入的竞态」，经基线 A/B 对照（改动全部 stash 后同样失败）后证伪并撤回；随后又误判为「恢复协程覆盖」，经探针实测再次证伪并修正。

**已修复**（提交见 `650b10b` 之后）：为缺失的 fake 补 `workspaceMaterialItems` 覆写，使工作台加载永不触网。零新依赖、不碰生产代码。验证方式见 `docs/decisions/ADR-001-测试基础设施改造.md` 与 `tasks/测试修复-验收标准.md`。

### 后端测试

全量运行 `23 failed, 52 passed`。**已 A/B 验证为基线既有**：对 stash 后的基线跑同一套全量测试，结果完全一致（23/52）。

逐文件隔离运行：**28/28 全部通过，0 失败**。

**根因**（经独立实测查明）：`app/main.py` 在 **import 时**把 `INITIAL_ADMIN_PASSWORD` 固化为模块常量，而 `app.main` 整个进程只被导入一次；各测试文件又在 import 期用 `os.environ` 写入**互不相同**的密码（`os.environ[...] = ` 硬写、`os.environ.update(...)`、`os.environ.setdefault(...)` 三种写法混用）。于是**首个被导入文件的密码胜出**，其余文件用自己的密码建库、却拿别人的密码登录 → 401 连锁失败。

`conftest.py` 原有的 `isolated_backend_database` fixture 只 monkeypatch 了 `DATA_DIR`/`UPLOAD_DIR`/`DB_PATH`，**未覆盖密码快照**，且原有一处补丁只针对 `test_password_change_policy.py` 单文件，因此挡不住跨模块污染。

**已修复**：在 `conftest.py` 内按测试文件自身声明的密码对齐模块常量（单点拦截，不改 24 个测试文件顶部散落的 `os.environ` 写法）。修复后全量 **75 passed / 0 failed**，连续 10 轮稳定。
