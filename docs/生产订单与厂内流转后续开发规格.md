# 生产订单与厂内流转后续开发规格

## 1. 范围

本规格用于 `feat/ui-fusion` 合并后的后续开发。系统只处理公司内部生产订单和厂内物料流转，不处理外部物流、承运商、运输轨迹、线边库或配送工位。

## 3. 数据结构定义

### 3.1 ProductionOrder

```text

  shortageCount: int         // >= 0
```

## 5. 事务与权限

- `INBOUND`、`OUTBOUND`：创建申请后必须审批；审批前不得修改库存。
- `RELOCATION`：单数据库事务内锁定来源库存行，校验版本和数量，再扣减来源并增加目标。
- `RETURN`：作为入库方向的独立流转记录，按入库审批规则处理。
- `STOCKTAKE`：提交实盘数量，仓库管理员确认差异。
- `ADJUSTMENT`：涉及库存变化时必须审批。
- 操作员可提交申请；物料员可提交申请和盘点；仓库管理员可审批和确认；管理员拥有全部权限。
- 同一用户不得审批并执行同一申请。
- 所有写接口必须接收 `Authorization` 和 `X-Request-Id`，服务端写入 UTC 时间。

## 6. 合并后验证清单

```text
[ ] MaterialFlowApi 不含真实 IP、HTTP 测试地址或密码
[ ] API 地址由未提交 local.properties / CI Secret 注入
[ ] AndroidManifest 生产构建不允许明文 HTTP
[ ] assembleDebug 成功
[ ] 后端 py_compile 成功
[ ] 生产订单扫码返回 PRODUCTION_ORDER
[ ] 厂内流转单扫码返回 FLOW_RECORD
[ ] 订单详情可展示多个机型
[ ] 机型详情可展示物料和厂内流转记录
[ ] 入库/出库审批门禁通过
[ ] 调拨库存不足和版本冲突时回滚
[ ] 公开仓库敏感信息扫描为空
```

## 7. 实施顺序

1. 先修复远端分支的 API 地址注入和旧运行时文案。
2. 再实现生产订单、机型和厂内流转接口。
3. 再接入订单详情和机型详情页面。
4. 再完成审批、执行和库存事务。
5. 最后补齐图片、离线持久化、WorkManager 和自动化测试。
6. 通过所有门禁后，用 PR squash 合并到 `main`。
