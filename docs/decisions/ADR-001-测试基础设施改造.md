# ADR-001: 测试基础设施改造 —— 消除 Android 跨类间歇失败与后端全量混跑污染

## Status

Proposed（2026-09-20）

## Context

仓库 `material-flow-system`（分支 `feature/ui-polish-camera`）的两个测试套件当前不可信，表现为间歇性失败与全量污染。改造目标：让测试从「约 50% 概率间歇失败」变成「确定性可重复」，且**尽量小、可回滚，不重构业务逻辑**（存量代码）。

### 问题 A：Android 单元测试跨类间歇失败（~50%）

- 现象：`LogisticsViewModel*` 系列测试类**混跑**时约 50% 概率失败；**单独跑任一测试类全部通过**。
- 已确认失败用例：`LogisticsViewModelUserManagementTest > deleteUserExposesLoadingThenSuccessAndRefreshesList`；`LogisticsViewModelAssemblyTest > removingAssemblyMemberUpdatesTaskAndReportsConflict`；`LogisticsViewModelAssemblyTest > assignmentFailureClearsLoadingAndExposesRetryMessage`。
- 实测（本轮，HEAD `650b10b`）：混跑 3 轮 = FAILED/SUCCESSFUL/FAILED；再 4 轮 = PASS/FAIL/PASS/FAIL；固定类顺序 8 轮 = FAIL 5/8。失败断言固定为 `LogisticsViewModelUserManagementTest.kt:38`：`expected:<u-1> but was:<null>`。

### 问题 B：后端测试全量混跑污染

- 现象：全量 `pytest` = **23 failed / 52 passed**；**逐文件隔离运行 8/8 全绿**（实测本轮 8 个失败文件单独跑全部通过）。
- 失败文件：`test_bom_order_concurrency_states.py`(5)、`test_bom_order_edge_cases.py`(4)、`test_r02_slice.py`(3)、`test_business_closure.py`(3)、`test_bom_order_remaining_gaps.py`(3)、`test_production_order_device.py`(2)、`test_bom_import.py`(2)、`test_order_material_summary.py`(1)。
- 典型失败：`tests/test_r02_slice.py:31` 断言 `response.status_code == 200` 实得 `401 Unauthorized`（`账号或密码错误`）。

### 独立验证的根因结论（与原始判断有出入，见「实测证据」）

- **问题 A 的真实根因不是**「`init` 内会话恢复协程后落地、覆盖 `login()` 写入的 ADMIN 登录态」。**真实根因是**：测试 fake repository **未覆写 `workspaceMaterialItems`（及部分类的 `workspaceSummary`）**，导致 `login()` 成功后的工作台加载回落到**真实 `MaterialFlowApi` 网络调用**（`Dispatchers.IO`）；该调用失败（环境返回 401）触发 `LogisticsViewModel.loadGenericWorkspacePage` 的 `onFailure → expireSession()`，把 `authState` 重置为 `Unauthenticated`（`role` 退化为 `OPERATOR`）；后续带角色守卫的方法（`deleteManagedUser` / `assignAssemblyMembers` / `removeAssemblyMember`）在守卫处提前 `return`，断言失败。该重置发生在 IO 线程上、时机不确定 → 间歇失败。
- **问题 B 的真实根因是**：`app/main.py` 在 **import 时**把 `INITIAL_ADMIN_PASSWORD`、`DATA_DIR`、`DB_PATH` 快照为模块级常量；而各测试文件在 **import 时**用 `os.environ[...] = ...` 或 `os.environ.setdefault(...)` 写入**互不相同**的管理员密码。`app.main` 只被 import 一次，最后一个「硬写」`os.environ[...]` 的文件胜出，其余文件（含用 `setdefault` 的）拿到的密码与自身 `_login()` 期望值不一致 → 401。`conftest.py` 的 `isolated_backend_database` 只隔离了 DB 路径，**未隔离密码快照**，故无效。

## Decision

### 决策 1（问题 A）：补全测试 fake 的 repository 覆写，消除对真实网络的隐式依赖；辅以 `runTest` + `StandardTestDispatcher` 统一调度

- **主修复（必须）**：为所有构造 `LogisticsViewModel(repository, scope)` 的测试类的 fake repository 补上缺失的 `override suspend fun workspaceMaterialItems(...)`（返回 `Result.success` 空页），使工作台加载**永不触网**。这是根因修复，最小、可回滚、不碰生产代码。
- **加固（建议，同一 ADR 内）**：把 `Dispatchers.Unconfined` + `CoroutineScope(SupervisorJob() + ...)` 的手工作用域，逐步替换为 `kotlinx-coroutines-test` 的 `runTest` + `StandardTestDispatcher`，让挂起点与等待点显式受控，杜绝「异步副作用在断言之后落地」这类时序耦合。
- **明确否决**：不改生产代码加测试钩子（例如暴露「恢复完成」信号）。真实根因不在生产代码的恢复协程（实测恢复协程在构造期确定性执行，`sessionGeneration` 守卫有效），加生产钩子既无必要，也违背「存量代码最小改动」。

### 决策 2（问题 B）：在 `conftest.py` 用**按模块对齐的** `INITIAL_ADMIN_PASSWORD` 覆写替代对 `os.environ` 快照的隐式依赖，并保留既有 DB 隔离

- **主修复（必须）**：在 `isolated_backend_database`（autouse fixture）内，除现有 `DATA_DIR/UPLOAD_DIR/DB_PATH` 的 monkeypatch 外，追加
  `monkeypatch.setattr(backend, "INITIAL_ADMIN_PASSWORD", <该模块自己的期望密码>)`。
  密码期望值由**测试模块自身声明**（如模块级常量或从该模块的 env 写入值解析），使每个模块的 `init_db()` 用自己期望的密码建库，全量混跑不再互相覆盖。
- **替代/补充**：把散落在 24 个测试文件顶部的进程级 `os.environ[...] = ...` 改为**模块级常量 + fixture 注入**，`app.main` 侧改为**惰性读取**（`INITIAL_ADMIN_PASSWORD` 由「import 快照」改为「调用时读取」）。此改动侵入生产代码 `app/main.py`，列为**可选后续项**，不纳入本次必须范围。
- **明确否决**：仅靠「逐文件跑」规避（`NEXT.md` 当前做法）。这只是掩盖，不满足「全量混跑确定性可重复」的验收目标。

## Consequences

### 正面

- 两个套件的失败**从时序相关变为确定性归零**：Android 主修复后，ADMIN 类测试不再触发 `expireSession()`；后端主修复后全量跑实测从 23 failed/52 passed 变为 **75 passed**（本轮以等价手段验证，见下）。
- 根因修复不改业务逻辑，可回滚（Android 仅改测试；后端仅改 `conftest.py`）。
- 消除「只因 CI 机器快慢不同就红/绿」的假信号，恢复测试作为契约的可信度。

### 负面 / 代价

- Android 需为约 3～6 个测试类的 fake 补齐 `workspaceMaterialItems` 覆写；若进一步引入 `kotlinx-coroutines-test`，需新增测试依赖并逐类改造 30 处 `Dispatchers.Unconfined`（本轮**未**引入该依赖，`build.gradle.kts` 中确无 `kotlinx-coroutines-test`）。
- 后端若选择「惰性读取」方案，会触碰生产代码 `app/main.py`（列为可选项，默认不做）。
- `os.environ` 进程级写入的清理不彻底时，仍可能在**新增测试文件**时重现同类问题；本 ADR 的 `conftest` 对齐策略只覆盖已知模块，需配套「新增测试文件须声明自身期望密码」的约定。

## 实测证据（本轮独立复现，均为受控实验）

### 问题 A

1. 混跑失败可复现：`./gradlew :app:testDebugUnitTest --rerun-tasks --tests "*LogisticsViewModel*"`，多轮 FAIL/PASS 交替；失败固定为 `UserManagementTest.kt:38 managedUserDeletingId=false(null)`。
2. 单类/单方法隔离 0 失败：单独跑 `LogisticsViewModelAssemblyTest`（5/5 通过）、单独跑失败方法（6/6 通过）、单独跑 `UserManagementTest`。
3. 成对实验锁定交互：`Assembly + UserManagement` = 失败 2/5；`Workspace + UserManagement`、`Routing + UserManagement`、`Handover + UserManagement` = 0/5。
4. 反编译驱动真实 `LogisticsViewModel` 的独立探针（JUnit，复用仓库编译产物），打印状态：
   - `after ctor = Unauthenticated`（恢复协程在构造期确定性执行）
   - `after login = Authenticated(ADMIN)`
   - `after 1.5s = Unauthenticated / role=OPERATOR`（异步工作台加载触发 `expireSession()`）
5. 相关性：未覆写 `workspaceMaterialItems` 的类 = `AssemblyTest`、`UserManagementTest`（均为 ADMIN 用例）→ 正是失败列表；已覆写的类（AdminRolePreview/ApprovalAudit/Handover/Workspace）→ 从不失败。
6. 修复方向验证：探针 fake 补上 `workspaceMaterialItems` + `workspaceSummary` 覆写后，`role` 在 1.5s 后仍为 `ADMIN`，3/3 稳定。

### 问题 B

1. 全量 `pytest -q` = **23 failed / 52 passed**（可复现）。
2. 8 个失败文件逐个隔离运行 = 全部通过。
3. 采集探针（`pytest` 插件，采集结束时读 `sys.modules["app.main"]`）：`INITIAL_ADMIN_PASSWORD = 'DeleteAdmin@2026'`，`DB_PATH = /tmp/mf_admin_user_delete_.../data/material_flow.db` —— 即 `test_admin_user_deletion.py`（按文件名序第一个 `from app import main` 的硬写文件）胜出。
4. 顺序双向验证：`r02 → delete` 时 3 failed（delete 的 8 个用例因密码不符失败）；`delete → r02` 时 8 failed（r02 失败）。两个方向都印证「谁先硬写 `os.environ` 谁定义全局密码」。
5. 修复方向验证：以等价手段（探针插件按模块对齐 `backend.INITIAL_ADMIN_PASSWORD` 为该模块源码中的期望值）运行全量 `pytest`，结果 **75 passed**（0 failed）。
