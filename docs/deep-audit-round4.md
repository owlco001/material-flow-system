# 第四轮：机台详情物料范围下推

基线d40aad6，本地分支fix-deep-audit-138ff95。后端0.22.3，Android0.5.55 / 62。未推送、未部署、未发布APK。

## 问题与实现

机台详情原按每个关联订单拉取全部物料，再在Android按机台过滤；其他机台物料同样耗费传输、解析和内存。隔离红测用6条需求（目标机台3条）证明旧接口忽略deviceNo，返回total=6。

后端POST /api/v1/orders/material-status请求体新增可选deviceNo，精确绑定当前订单中的order_devices.device_no。total、明细分页、materialSummary、shortageLineCount全部复用同一个参数化范围。未传deviceNo时保持整单口径；不存在的机台返回空集合，不回退整单；空/非字符串拒绝。保留历史导入的长编号，不以手工创建接口64字符限制误伤历史数据。分页排序添加r.id稳定尾键，超大offset限制到SQLite可表示的整数范围。

Android旧orderMaterialStatus的默认调用不变。新增Repository.deviceOrderMaterials，每次200行、每页携带deviceNo，顺序取完目标机台所有页；检查身份、文档号、连续页码和空页hasMore，异常响应返回失败而不静默截断。机台详情只调用该路径并对关联订单去重，客户端继续按deviceId/deviceNo作防御过滤。旧服务端忽略筛选但支持分页时仍遍历各页后过滤，正确但没有新性能收益；更老无分页元数据响应按完整一页处理。

## 证据

- 修复前机台过滤红测：目标3条仍返回total6。
- 独立复核发现64字符限制与U9/聚合历史导入不兼容；长编号fixture返回400的红测后去掉该新增限制。
- 后端覆盖机台两页不重不漏、汇总/缺料同范围、旧整单口径、未知/injection-like编号空集合、空白编号校验、历史长编号。
- Android真实本地HTTP覆盖7项：每页筛选/后页完整、重复错误页、空页冒充more、防御过滤、长编号无截断、旧服务端目标在后续页、无分页元数据旧响应。

合成100台、每台200条需求（总20,000），同机真实handler三次中位值：

| 指标 | 整单 | 单机台 |
|---|---:|---:|
| 返回需求行 | 20,000 | 200 |
| JSON字节 | 7,708,617 | 129,585 |
| handler中位耗时 | 137.268 ms | 3.514 ms |

JSON含各自范围的完整汇总。时间不含HTTP/鉴权/真实网络，不外推生产。性能回归断言行数和字节预算，不使用绝对耗时阈值。
