## 2. 「修好了」的量化判据（核心）

> 间歇性问题的最大陷阱：跑一次绿了就当修好。判定必须建立在**重复运行 + 结果确定性**之上。

### 2.1 定义三个判定量

- **D（Determinism，确定性）**：同一提交、同一命令，重复运行 N 次，**N 次全部通过**。
- **R（Repetition，重复次数）**：见 2.2 取值与依据。
- **K（Kill，变异杀伤）**：注入畏惧缺陷后，**至少一个**原本存在的测试变红。

### 2.2 重复次数 N 的取值与依据（不拍脑袋）

**问题 A（Android 混跑）取 N = 20 轮；问题 B（后端全量）取 N = 10 轮。**

依据（二项分布，零容忍上限）：
- 设单轮仍偶发失败的概率为 p。要宣称「已消除间歇性」，需保证在 N 轮里**观察到 0 次失败**时，真实残存失败率 p 足够低。
- 取 N 轮全绿，则残存失败率的上界（95% 置信）近似为 `p_upper ≈ 3/N`。
  - Android N=20 → `p_upper ≈ 15%`……不够严，故 Android **N=20 且叠加 2.4 的“乱序/并发触发”**（见下），实测基线失败率约 62%，20 轮全绿的误判概率 ≈ `0.38^20 ≈ 1.6e-9`，足以排除「碰巧全绿」。
  - 后端 N=10，基线为**确定性全红**（23 条稳定失败，非概率性），修复后要求 10 轮全绿；由于基线是确定性的，10 轮足以验证「污染已消除」，并覆盖收集顺序扰动。
- **附加要求（问题 A 关键）**：Android 的间歇性来自「类顺序不确定」，因此 20 轮中**至少 10 轮必须启用测试类乱序或并发执行**，不能只靠固定顺序重跑凑数。乱序手段：多次 `--rerun-tasks`（JUnit 执行顺序本身不保证稳定）即可，若引入 `maxParallelForks>1` 需在证据中声明。

> 说明：N 是**最低门槛**，不是充分条件。必须叠加 §2.4 变异测试与 §3 红线检查才算完整判定。

### 2.4 反向验证：变异测试（证明测试仍然有效）

> 一个「永远通过」的测试也是垃圾。修复后必须证明测试仍能抓到缺陷。注入点与期望失败断言如下，**修复者必须逐项执行并留证**。

#### 变异 M1（Android · 角色守卫）— 对应问题 A 的核心语义

- **注入点**：`logistics-android/app/src/main/java/com/company/logistics/ui/LogisticsViewModel.kt`，`deleteManagedUser` 的角色守卫（约 :440）。
- **注入方式**：把
  ```kotlin
  if (_state.value.role != UserRole.ADMIN || _state.value.preview || userId.isBlank()) return
  ```
  改为
  ```kotlin
  // MUTATION: 去掉角色守卫
  // if (_state.value.role != UserRole.ADMIN || _state.value.preview || userId.isBlank()) return
  ```
- **期望结果**：修复**后**的测试应当**变红**——去掉守卫后，若测试真能在登录态下调用 `deleteManagedUser`，则 `managedUserDeletingId` 会被置位，`assertEquals(2, repository.listUsersCalls)` 等断言**不会**失败但 `assertTrue(repository.deleteOperationId != null)` 仍成立；因此**真正的判定信号是：断言集合中必须存在能区分「守卫生效」与「守卫被移除」的用例**。
- **期望失败断言**：`LogisticsViewModelUserManagementTest.deleteUserExposesLoadingThenSuccessAndRefreshesList` 中 `assertEquals("u-1", viewModel.state.value.managedUserDeletingId)`。
- **判定**：若去掉守卫后测试**全绿** → 测试对该守卫无覆盖 → **C7 不通过，打回**。
- **注意**：原设计的「去掉 `restoreGeneration` 守卫」注入点**已废弃**——该守卫并非真因（见 §0 根因修正），去掉它不会让测试变红，会造成误判。

#### 变异 M1b（Android · 未打桩触网，真因验证）

- **注入点**：测试侧，`LogisticsViewModelUserManagementTest.kt` 的 fake repository 中 `workspaceMaterialItems` 覆写。
- **注入方式**：注释掉该覆写，使其回落到真实 repository。
- **期望结果**：修复**后**的测试应当**变红或至少变得不确定**——这正是问题 A 的原始机理。若注释掉后测试**依然 100% 全绿**，说明修复并未真正隔离网络调用，而是靠时序碰巧躲过 → **C7 不通过，打回**。

#### 变异 M2（后端 · 幂等计数）— 对应问题 B 的核心语义

- **注入点**：`material-flow-backend/app/main.py` 中 production-order 幂等写入逻辑（`test_concurrent_order_idempotency_creates_one_order_and_model` 断言「恰好 1 条 `idempotent is False`」「`COUNT(*)=1`」所对应的写入/去重分支）。
- **注入方式**：在幂等键校验处**短路 one_shot**，例如把幂等命中判定取反或跳过，使其重复写库。
- **期望结果**：`test_bom_order_concurrency_states.py::test_concurrent_order_idempotency_creates_one_order_and_model` **变红**。
- **期望失败断言**：`assert sum(r.json().get("idempotent") is False for r in responses) == 1` 或 `assert c.execute("SELECT COUNT(*) FROM production_orders WHERE order_no='SO-CONCURRENT'").fetchone()[0] == 1`。
- **判定**：若注入后仍全绿 → 断言是空的 → **C7 不通过，打回**。

#### 变异 M3（联动 · 证明修复没有把测试改松）

- **注入点**：任选一个基线**原本通过**的用例所保护的逻辑（例如 `test_material_actions.py::test_complete_actions_permissions_idempotency_inventory_audit_and_workspace` 对应的权限/幂等分支）。
- **注入方式**：破坏其核心不变量（如权限判断取反）。
- **期望结果**：该用例变红，且**全量轮次**中恰好该条红、其余绿（证明测试仍能定位）。
- **判定**：若发现新修复引入了「连带全绿」或该条不再变红 → 怀疑断言被削弱 → 转 §3 R2 审查。

> 三个变异必须**逐项执行、逐项留证（注入 diff + 运行输出 + 失败断言原文）**，并在完成后**还原注入**（`git checkout -- <file>`）。还原后必须重跑 §2.3 C1/C2/C4 确认回到全绿。

## 3. 红线清单（不许做什么）

> 修理间歇性测试时，以下行为是**作弊**，不因「让 CI 变绿」而豁免。出现任一即 P0 阻断。

### R1 禁止重试掩盖
- **禁止**：`@Retry` / `pytest-rerunfailures` / `--reruns` / Gradle `testRetry` 插件 / 自写 `while(fail) retry` 包装 / `flaky` 库。
- **理由**：重试把「竞态未消除」伪装成「偶发」，是把问题藏起来而非解决。
- **检测**：
  ```bash
  # Android
  grep -rniE "retry|rerun|flaky" logistics-android/app/build.gradle* logistics-android/build.gradle* logistics-android/app/src/test --include="*.kt"
  # 后端
  grep -rniE "reruns|rerunfailures|flaky" material-flow-backend/tests material-flow-backend/*.ini material-flow-backend/*.cfg material-flow-backend/pyproject.toml 2>/dev/null
  # 命令参数
  git diff 650b10b..HEAD | grep -iE "reruns=|--reruns|retry"
  ```
- **期望**：全部无输出。出现在**测试代码**里的 `retry` 变量名不算违规，但若是重试循环/注解即违规。

### R2 禁止删除或削弱断言
- **禁止**：`assertEquals`→`assertNotNull`/`assertTrue`、放宽容差、删除关键断言、`try/except: pass` 吞断言、`assert x == y, "always"` 之类恒真断言。
- **检测**（基线对比，基线见 §2.3 C6）：
  ```bash
  # Android 断言总数（修复后必须 >= 521）
  grep -rn "assertEquals\|assertTrue\|assertNull\|assertNotNull\|assertThrows\|assertNotEquals\|assertFalse" \
    logistics-android/app/src/test --include="*.kt" | wc -l
  # 后端断言总数（修复后必须 >= 767）
  grep -rn "assert " material-flow-backend/tests --include="*.py" | grep -v __pycache__ | wc -l
  # 逐文件断言数下降检测（对抗"删一处补一处"）
  git diff 650b10b..HEAD --stat -- '*Test.kt' '*test_*.py'
  ```
- **期望**：断言总数不得低于基线；任一测试文件断言数**净减少**必须逐条解释并经裁判批准，否则打回。

### R3 禁止用固定延迟「等待」
- **禁止**：在测试中用 `Thread.sleep(...)` / `delay(固定值)` / `await(固定毫秒)` 来「等竞态过去」。
- **理由**：固定延迟掩盖竞态而非消除竞态，且使测试变慢仍不稳。
- **检测**：
  ```bash
  grep -rnE "Thread\.sleep|sleep\(|delay\([0-9]+\).*//|await\([0-9]+\)" \
    logistics-android/app/src/test --include="*.kt"
  # 后端（若测试里 sleep 等待线程/DB）
  grep -rnE "time\.sleep" material-flow-backend/tests --include="*.py" | grep -v __pycache__
  ```
- **期望**：无输出。**正确做法**：Android 用 `StandardTestDispatcher` + `advanceUntilIdle()` / `runTest` 控制虚拟时间并显式等待 `job.join()`；后端用 fixture 强制每文件独立 DB / 进程级隔离，而非 sleep。

### R4 禁止产品代码为测试让路
- **禁止**：改 `main/`（Android）或 `app/`（后端）产品逻辑来配合测试，除非架构师方案明确论证并经项目总监批准。
- **检测**：
  ```bash
  git diff 650b10b..HEAD --name-only -- \
    'logistics-android/app/src/main/**' 'material-flow-backend/app/**'
  ```
- **期望**：无输出。若确需改动（例如修复真实的竞态缺陷），必须单独提交、单独论证、单独评审，并与测试修复 diff **分离**。

### R5 禁止静音失败用例
- **禁止**：`@Ignore` / `@Disabled` / `pytest.mark.skip` / `skipif` / `xfail` / 注释掉 `@Test` / 删除测试方法。
- **检测**：
  ```bash
  # 基线（650b10b）对比：新增以下标记即违规
  grep -rn "@Ignore\|@Disabled" logistics-android/app/src/test --include="*.kt"
  grep -rn "skip\|xfail\|@pytest.mark.skip" material-flow-backend/tests --include="*.py" | grep -v __pycache__
  # 测试方法总数不得减少（基线：后端 def test_ = 70）
  grep -rn "def test_" material-flow-backend/tests --include="*.py" | grep -v __pycache__ | wc -l
  grep -rn "@Test" logistics-android/app/src/test --include="*.kt" | wc -l
  ```
- **期望**：新增 skip/ignore 计数 = 0；测试方法总数不减少。

### R6 禁止篡改门禁/配置掩盖
- **禁止**：调低覆盖率阈值、关闭必过检查、在 conftest/build.gradle 用 try/except 或全局 hook 吞掉失败。
- **检测**：`git diff 650b10b..HEAD -- '**/conftest.py' '**/build.gradle*' '**/pytest.ini' '**/pyproject.toml'`，逐行审查是否有吞异常/放宽阈值。

| E4 | 混跑 N 轮完整输出 | 文本 | Android 20 轮、后端 10 轮的逐轮结果（§4） |
| E5 | 单类/单文件回归输出 | 文本 | 证明未曾通过「删测试」来变绿 |
| E6 | 变异测试证据 | 3 段 | M1/M2/M3 各自的注入 diff + 注入后失败输出 + 还原后重跑全绿输出 |
| E7 | 红线扫描输出 | 文本 | §3 R1–R6 全部检测命令的**空输出**证据 |
| E8 | 数量守恒表 | 表 | 修复前/后：测试文件数、`@Test`/`def test_` 数、断言总数（Android 与后端） |
| E9 | 新增测试依赖声明 | diff | 若引入 `kotlinx-coroutines-test` 等，须在 build.gradle 声明并说明**用途是控制虚拟时间而非重试** |
| E10 | 一份回归用例 | 代码 | 将本次竞争/污染复现固化为可重复运行的回归用例（Android `tests/regression/` 或后端独立 `test_regression_*`） |

## 6. 「什么情况算失败」（直接打回条件）

满足任一即 `fail`，整包打回，**不接受「大部分绿」**：

1. **通过率非 100%**：Android 混跑 20 轮或全量 10 轮中出现**任何 1 轮 ≥1 failed**；后端全量出现任何 `failed`。
2. **靠 retry/rerun 达成通过**：R1 检测命中（新增重试配置、命令带 `--reruns`、代码含重试循环）。
3. **断言被削弱或删除**：R2 断言总数低于基线，或任一测试文件断言净减少无正当理由。
4. **测试数量减少**：`def test_` < 70 或 `@Test` 数减少（有人删测试）。
5. **变异测试抓不住注入缺陷**：M1/M2/M3 中任一注入后测试仍全绿（C7 不通过）。
6. **使用固定延迟等待**：R3 命中 `Thread.sleep`/固定 `delay`。
7. **产品代码为测试让路**：R4 命中 `main/` 或 `app/` 非空 diff 且无批准论证。
8. **静音失败用例**：R5 命中新增 `@Ignore`/`skip`/`xfail`。
9. **篡改门禁**：R6 命中覆盖率阈值/必过检查被放宽。
10. **证据缺失**：E1–E10 任一缺失。
11. **不可复现的结论**：修复者声称「已修复」但无法提供 N 轮原始输出，或输出与声明不符。

> 打回必须**诊断式**：指明「违反第 X 条 + 证据（哪条命令输出/哪段 diff）+ 期望值」，不接受泛泛退回。

## 7. 生产就绪评级（本次修复的目标档）

按记分卡 7 维 × 3 档，本次修复仅影响「测试 + 回归」维度，目标为 **Silver**：

| 维度 | 目标档 | 判据 |
|------|--------|------|
| 测试 + 回归 | **Silver** | 回归率为零（无由绿转红）、关键路径可重复通过、变异加固存在杀手测试 |
| 其余 6 维 | 维持现状 | 本次不涉及 |

**总档取最低 = Silver**。未达 Silver（即上述任一判定量不达标）不得宣布测试可信。
