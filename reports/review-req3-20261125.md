## 二、问题清单（按优先级，含修法）

### P0-1 默认同步永远学不到「关闭」，已结案单永久计在途

- 位置：`app/u9/client.py:642,695-698`（`only_open` 在客户端丢弃关闭单）、`app/u9/sync.py:899-1035`（只 upsert 本次返回的单，不刷新/不清理）、`app/u9/routes.py:132`、`app/templates/u9.html:104`（默认 true）
- 影响：采购把单关了，本地仍算在途/已到货；料号永远不落 NO_PLAN，采购不会补单，仓库也不会催。与验收项「已关闭 PO 不计在途」在默认路径上直接冲突；`docs/shortage-status.md:71,179` 还宣称「已结案订单不算在途」。
- 修法（二选一，推荐 A）：
  - A. 同步默认 `only_open=false`（读取侧 `main.py:5629` 已按状态过滤，存关闭单无害），模板复选框改为「同时同步已结案订单（用于识别关闭，推荐）」并默认勾选；日志/文档同步改口径。
  - B. 保留 `only_open=true`，增加一轮「状态刷新」：把本地仍 open 的 `doc_no` 列表（180 天窗口内约 2–4k）用 `DocNo IN (...)` 查一次状态并回写；或对「本次窗口内未返回但本地 open」的单据置为 closed/删除（需先有稳定的 `OrderBy` 与窗口判定，避免误删）。
- 必须补的回归用例：sync(Approved) → 改 Closed → 默认参数再 sync → `inTransitQty==0`、`openOrderCount` 减 1、状态落 NO_PLAN。

### P1-1 `UNKNOWN_MATERIAL` 在生产规模下整段被跳过，且与「全部识别」不可区分

- 位置：`app/u9/sync.py:879-883`（`len(codes) > 2000` 直接跳过）、`app/main.py:5571-5590`（`unknownMaterials=[]` 与「核对通过」同形）、页面 `project_kitting.html:62-63` 只显示计数
- 证据：只读库副本上 `COUNT(DISTINCT m.code)`（需求行 JOIN materials）= **2,762 > 2,000**，所以现网第一次同步就会写一条 errors「本次跳过料号体系核对」，`unknownMaterials=[]`，页面显示「查不到 0 个」——需求 4 的「料号体系不一致 → UNKNOWN_MATERIAL」在真实数据上等于没做。
- 修法：删掉 2000 上限，按 `cfg.batch_size` 分块调 `fetch_items`（它本来就分批，`client.py:390-395`），或分块 2000 循环；若坚持上限，`detail` 里写 `itemsCheck: "skipped"`（而不是 `unknownMaterials: []`），响应加 `poData.itemsChecked=false` 并在页面提示「料号核对未执行」，同时补单测。

### P1-2 采购行集合形态未验证，最坏会把全量状态压成 NO_PLAN 且 `fresh=true`

- 位置：`app/u9/client.py:665-686`（去重键只有 `DocNo`）、`app/u9/mappers.py:363-373`（`po_raw_lines` 只认 `POLines` 列表/单对象）、`app/u9/mappers.py:383-386`（没有行就跳过行字段校验）、`app/u9/sync.py:929-934`（`headers` 按 doc_no 覆盖）
- 风险：`CommonEntity/Query` + `ReturnFields=POLines.*` 若按「一行一条扁平记录」返回（这类查询接口常见），`po_raw_lines` 返回 `[]` → 每张单 0 行 → 校验因「没有行」直接放过 → 所有料号 `inTransit=0`、`arrived=0`，`fresh=true`，页面看起来「刚同步过、没有任何在途」→ 采购重复下单。这正是提交里反复强调要避免的方向。分页还会叠加：第 2 页若全是已见 `DocNo` 的其余行，`novel==0` 直接 break，静默截断。
- 修法：`po_raw_lines` 增加扁平回退（`DocLineNo`/`ItemInfo.ItemCode`/`PurQtyTU`/`TotalRecievedQtyTU` 在同级时合成一条行）；`validate_po_rows` 增加「有单但总行数为 0，且响应里出现行字段扁平键」→ 抛错；分页去重键改成 `(DocNo, DocLineNo)`（扁平形态下才唯一）；补一条扁平形态单测。上线前用「预览同步」核对 `stats.lines` 与 U9 `PM_POLine` 行数同量级（sample 里已带「行数」可直接看）。

### P2

1. **快照整表聚合，每次翻页都付 224–251 ms**（`main.py:5623-5628`）。建议按本页料号收窄：`WHERE l.item_code IN (...)`（沿用 5894 的分块写法），或按 `MAX(synced_at)` 做进程内 TTL 缓存。

4. **分页无 `OrderBy`**（`client.py:672-686`）：SQL Server 无稳定排序时 `PageIndex` 分页可能重/漏，配合 `novel==0` 会静默少同步。建议请求体带 `OrderBy: "DocNo"`（或 ID），并记录本次总页数/total 供对账。

6. **UNKNOWN 抢在档 1 之前**（`main.py:5677-5678`）：料号在 U9 档案缺失但本地有库存时，应显示「在库可满足」而不是「料号未识别」。建议先跑 1→4，仅当结果为 NO_PLAN 时再用 UNKNOWN_MATERIAL 覆盖。
7. **组织隔离缺失**（`sync.py:1010` 存 `org_code`，`main.py:5623-5628` 从不用）：多组织 U9 会把别家 PO 算进在途。查询条件加 `Org`，或读取侧过滤 `h.org_code=cfg.org_code`。
8. **`stale` 无测试、提示偏弱**（`main.py:5647`、模板 60-63）：只改了文字色，且旧版无时区 `started_at` 会按 UTC 解析，标黄晚 8 小时。补一个「synced_at = 25h 前 → stale=true / 页面出现提示」的用例。
9. **0 张同步仍置 fresh**（`main.py:5611-5618`）：U9 侧字段/实体名一改就返回 0 张，页面却显示「刚同步过」。建议 `total==0 且已有数据` 时降级为 stale 或加「本次同步 0 张」提示。
