### 3. 层级还原 —— 现场数据正确，跳级时会挂错子树

用生产库最新批次 `09c05196…`（25,955 行 / 118 台 + 1 个空编码组 1,556 行 / 1-6 层）复刻 `_pmr_build_tree` 全量跑：

- 119 组、25,955 节点、**0 个节点实际深度 ≠ level_no**；13,815 行走 `parent_code`、12,021 行走层级栈、119 个根。现场数据（parent_code 全是设备根、line_no 是 DFS 序）**还原正确**。
- 任务里担心的「同层兄弟间夹着其他子树深层行」在 DFS 序下**不会挂错**：栈里 `last_at_level[level-1]` 就是最近的上一级。已构造场景 A 验证（`A/a1/a1x` 之后 `B/b1` 之后再来 `b2`）结果正确。
- **真正的缺陷在「跳级」**：`parent = last_at_level.get(level-1)` 命中后直接返回（main.py:4916-4919），不会校验该节点是否已被更浅的行"关闭"。只要某机台缺了一整层（导入丢行 / ERP 只导 2、4 层），节点就会挂到**兄弟子树的深层节点**上，且 `shallower` 回退（4920-4923）永远走不到。已用真实函数复现：

```
输入: R(1) → A(2) → a1(3) → a1x(4) ; B(2) ; b1(4, parent_code 空)
实际: R → A → a1 → {a1x, b1} ; B
期望: b1 挂在 B 下
```

  正确写法是维护「未闭合节点栈」：读入 level=L 的行时，先 pop 所有 `level >= L` 的节点，`parent = stack[-1]`。现场数据 0 例触发，但这是静默错挂（不报错、不告警），属于 P2 里最该修的一条。

### 5. 性能 —— 今天够用，没有任何上限

### 7. 测试质量 —— 覆盖了对的主线，但避开了几个最容易错的点

### 8. 导出 xlsx —— 结构合法、无公式注入，但控制字符会毁掉整个文件

- 实现其实是标准 OOXML（inlineStr），不是 docstring 写的 SpreadsheetML（xlsx_writer.py:2-8，措辞误导，不影响功能）。6 个 part 齐全，`[Content_Types].xml` 覆盖 workbook/sheet/styles，关系链完整，逐 part 用 `ElementTree` 解析全部通过；中文表头 + `xml:space="preserve"` 正常，自研 `XlsxSheetReader` 回读 25,956 行表头一致。
- **公式注入不成立**：`=1+1` 写进 `<c t="inlineStr"><is><t>=1+1</t></is></c>`，Excel 按文本处理（已验证生成物中就是 inlineStr）。料号以 `=`/`+`/`@` 开头不会被求值。
- **真问题**：`escape()` 只转 `& < >`，不过滤 XML 1.0 非法控制字符（xlsx_writer.py:76-79）。品名/规格里只要有一个 `\x0b`（Excel 复制粘贴常见）或 `\x01-\x08`，`sheet1.xml` 就不是良构 XML，Excel 打开会报"文件已损坏"。已复现：`ET.fromstring` 直接 `invalid token`。修法一行：`re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f]", "", text)`。
- 环境里没有 openpyxl / LibreOffice，**无法做独立于自研 parser 的打开验证**；建议 CI 加一条 `openpyxl.load_workbook` 或 `libreoffice --convert-to csv` 的冒烟。

### P2（建议改，不阻塞）

**P2-1　层级跳级时挂到兄弟子树的深层节点**
`app/main.py:4914-4923`
`last_at_level.get(level-1)` 命中即用，不判断该节点是否已被更浅的行"闭合"；`shallower` 回退因此永远走不到。复现：`R(1)→A(2)→a1(3)→a1x(4); B(2); b1(4, parent 空)` → `b1` 挂到 `a1` 下（应为 `B` 下）。现场数据 0 例，但丢层导入会静默错挂。
建议：`open_stack: list[tuple[int, node]]`，读入 L 行前 `while stack and stack[-1][0] >= L: stack.pop()`，`parent = stack[-1][1] if stack else None`；`parent_code` 命中后仍保留（优先），但命中节点必须还在栈里（未被闭合）。补跳级用例。

`app/main.py:5105`、`5129`；UI `templates/:108`、`:136`

建议：改为"叶子件用量合计"或"按料号去重后的合计"，并在字段名/表头注明口径；数字格式化到 2 位。

**P2-3　"项目公共"组被当成一台机台，设备数自相矛盾**
`app/main.py:5125`、`5101-5104`
26B-012 空 `device_code` 的 1,556 行被建成一个 `linked=false` 的组，`stats["deviceCount"]` 也 +1 → 页面显示"**119** 台机台（项目共 **118** 台）"。

**P2-4　导出的"父件料号"是原始列，不是树里真实的父件**
`app/main.py:5269`
U9 数据里 3/4 层行的 `parent_code` 全是设备根，导出会出现"料号 30101010-00016 的父件 = 60926012-00007"，而它实际嵌在 `50201-00320` 下（层级列却是 4）。计划员按父件列筛选会得到错误结论。
建议：导出写 `node` 的实际父件（建树时记 `parentCodeResolved`），原始列改名"原始母件料号"或干脆去掉。

**P2-5　未匹配组的"匹配来源"标成"项目名称匹配"**
`app/main.py:5112`、`5281`
即使批次是按 `device_no` 命中的，只要某组 `device_code` 认不到机台，`matchedBy` 一律写 `project_name`，导出显示"项目名称匹配"，与页面顶部的"机台号精确匹配"互相矛盾。

**P2-6　按机台过滤时静默丢弃"项目公共"段**
`app/main.py:5068`
26B-012 有 1,556 行空 `device_code` 的项目公共层级；`device_no=` 一过滤就整段消失（`if ... or device_no: continue`），单台视图和单台导出的物料清单不完整且无提示。
建议：`device_no` 过滤时保留公共组（标 `linked=false, matchedBy="common"`），或在页面/导出头部注明"不含项目公共层级 N 行"。

**P2-7　`expand=all` / 导出无上限、无分页、非流式**
`app/main.py:5054-5057`、`5293-5299`、`5337`
实测 26k 行 10.4 MB / 0.39 s、导出 1.86 MB / 0.82 s / 峰值 184 MB 尚可；批次规模涨 10 倍即 GB 级。
建议：`MAX_PMR_ROWS`（如 200_000）超限返回 409 并提示按机台导出；导出改 `zipfile` 流式写；`expand=top` 在建树时按 `keep` 截断，省掉 90% 无用功。

**P2-8　xlsx 控制字符 + 缺独立打开验证**
`app/xlsx_writer.py:76-79`

**P2-9　`_pmr_payload` 不自带鉴权，依赖调用方**
