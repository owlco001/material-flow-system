### P2 建议

**P2-1｜`LogisticsRepository.kt:664-675`｜解包缺少来源标记，用户备注若恰为合法 JSON 会被误判**
`unpackQueuedTransferRemark` 只判断 `JSONObject(raw).has("documentNo")`。如果用户在线下出库时手输的备注本身就是形如 `{"documentNo":"OM-9"}` 的合法 JSON，它会被当成打包结构，`documentNo` 被替换成 `OM-9`，单据挂到错误订单（后端只校验订单存在，不校验归属），齐套/追溯统计跟着错。
建议：打包体加版本标记（如 `put("v", 1)`，解包要求 `optInt("v")==1`），把"我们的结构"和"用户文本"区分开；`packQueuedTransferRemark` 的字段语义不变，只是多一个键，向后兼容仍需容忍无 `v` 的老打包体。

**P2-2｜`LogisticsRepository.kt:664-675` vs `834-839`｜新格式记录损坏时静默成功，与 RETURN/RELOCATION 处置不一致**
RETURN/RELOCATION 解析失败 → `FAILED("队列数据损坏，无法重放")`（`837`），会进"待处理"计数、用户可见；而 OUTBOUND 的打包体被写坏（DB 半写、迁移、人工改表）时，会被当成"旧裸文本"降级重放，**丢 `documentNo` 且标 SYNCED**，等于把本次要修的"齐套漏计"悄悄复活，而且没有痕迹。
建议：区分两类输入——`raw.trimStart().startsWith("{")` 且 `has("documentNo")` 失败/解析失败时判为损坏（`FAILED`），否则按旧裸文本降级。当前实现满足验收第 2 条，所以不算阻断。

**P2-3｜`app/main.py:4293-4302`｜成员现在能看到订单级（非本机台）的交接/流转事件**
`entity_ids` 包含该订单全部 `material_handovers` 与 `document_no=order_no` 的全部 `transfer_requests`，不是按 `visible_task_ids` 收敛的。这与 LEAD 一致，符合验收口径，但严格讲属于"同订单其他机台的数据"，建议产品侧确认这是期望的（若是，可在验收文档里写明；若不是，另开单按任务/机台收敛）。

**P2-4｜`tests/test_order_detail_assembly_members.py:104-114`｜缺"成员跨订单仍 403"一条**
目前只覆盖了 outsider（与 OM-1 无关）和已被移除的成员对 OM-1 的 403，没有覆盖"OM-1 的合法成员去请求 OM-2"。跨订单是最容易在改谓词时写漏的方向（只要把 `order_no` 条件写丢就会全绿）。
建议补两行断言：`asm-member` 请求 `OM-2/detail` → 403、`OM-2/tasks/task-o1` → 403。

**P2-5｜`app/main.py:4266`｜用 `str.replace("assembly_tasks","t")` 做 SQL 别名改写，脆弱**
现在安全（已核对 `"assembly_task_members".count("assembly_tasks") == 0`，实测为 0；子查询里的 `assembly_tasks.id` 被正确改写成 `t.id`，测试也通过）。但这是字符串级改写：将来谁在 `task_where` 里写一句含 `assembly_tasks` 的注释或起一个以 `assembly_tasks` 开头的别名就会被打断，而且失败方式可能是 SQL 报错而不是测试红。
建议：让 `task_where` 直接以别名 `t` 编写（订单级放行那段 `4236-4239` 已经是这样写的），去掉 `.replace()`。

**P2-6｜`LogisticsIconsCoverageTest.kt`｜未实证能在 JVM 单测里跑通**
该测试在纯 JVM 单测（无 Robolectric）里实例化 `ImageVector`，`build.gradle.kts` 未设 `unitTests.returnDefaultValues`。静态看 `icon()`（`ScannerComponents.kt:381-390`）只用到 `Dp / Color / PathBuilder`，不碰 `android.*`，判断可通过；但本次按要求未构建，这点没有实证。
