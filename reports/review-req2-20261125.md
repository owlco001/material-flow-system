## 一、必须先改（P1）

### P1-1 管理台关键字搜索对 WAREHOUSE_ADMIN 返回 JSON 403
- **文件:行**：`app/admin_web.py:1941`
- **问题**：`_kitting_page_state` 直接调用 API 函数 `api_list_projects(q=keyword, limit=20, user=user)`，而 `list_projects` 内部先执行 `_pmr_authorize`（`app/main.py:5192`），对 WAREHOUSE_ADMIN 抛 403。`_kitting_page_state` 没有捕获这个 ApiError，被全局异常处理器转成 JSON。实测（`/tmp` 隔离库、真实 TestClient）：

  ```
  wh1 login 303  search status 403  ctype application/json
  {"error":{"code":"FORBIDDEN","message":"无权查看项目物料需求",...}}
  ```

  `KITTING_WEB_ROLES`（admin_web.py:1899）和侧栏入口都放开了仓库，唯独搜索框不可用；仓库只能先知道精确项目号才能查，与需求第 4 条「WAREHOUSE_ADMIN 可查（仓库需要催料清单）」冲突。
- **修法**：抽一个不鉴权的项目搜索辅助函数（SQL 与 `list_projects` 同源、复用 `_pmr_like`，ASSEMBLER 分支保留），页面调用它；或在 `_kitting_page_state` 捕获 `ApiError` 并落到 `error=`。补一条「WAREHOUSE_ADMIN 按 q 搜索返回 200 且出现候选」用例。

### P1-2 缺口只看 `in_stock`，已全量到货的行被算成缺料（口径过严，数据相关）
- **文件:行**：`app/main.py:5398-5400`（`_kitting_gap`）、`app/main.py:5457-5472`（`_kitting_accumulate`）、`docs/kitting-shortage.md:20-23`
- **问题**：`gap = max(required - in_stock, 0)`，`arrived_quantity` 完全没参与。表上约束是 `in_stock <= arrived <= required`（schema CHECK），所以「已全量到货、尚未入库」= `arrived==required, in_stock=0` 的行会被判为缺口=required、且不进齐套。实测 26B-013：

  | 口径 | 齐套行 | 齐套率 | 缺口合计 |
  | --- | --- | --- | --- |
  | 当前（required − in_stock） | 9/90 | 10.0% | 1543 |
  | 按到货（required − arrived） | 61/90 | 67.8% | 531 |

  其中 52 行 `ARRIVED + arrived==required + in_stock==0`，合计贡献 1005 件「假缺口」。反过来 26B-012 的 32 行 ARRIVED 全部是部分到货（`arrived<required`），当前口径在那批数据上是正确的——所以这不是「部分到货被算齐套」（那一点实现是对的），而是对「已全量到货」的过度纠正。
- **修法**（二选一，需产品确认）：
  - **A（推荐）**：面向催料的缺料清单用 `max(required - arrived, 0)`；齐套行 = `status ∈ (ARRIVED, IN_STOCK)` 且 `arrived >= required`。既挡住部分到货虚高（需求文档的本意），也不把已到货算缺料。
  - **B**：保留 `in_stock` 作「备料齐套」，但 API 与 xlsx 必须增加「已到货量 / 待入库量」列，并把「总缺口量」改名为「备料缺口（需求−在库）」。
  - 无论选哪个，补一条 `arrived==required & in_stock==0` 的用例锁住。

## 三、8 条必查逐项结论

### 1. 齐套率口径：恒等式成立、部分到货不被算齐套、空项目为 null；但对「已全量到货」过严
- **恒等式成立**：`_kitting_accumulate` 先算 gap，`gap>0` 进缺料；否则 `status ∈ (ARRIVED, IN_STOCK)` 进齐套，其余进 `zeroGapLineCount`（main.py:5457-5472）。三支互斥且覆盖全部计入行，故 `需求行 = 齐套 + 缺料 + zeroGap` 恒成立。真实库 7 个项目逐个复算，全部 `identity=True`（含 26B-012 的 20552 行）。
- **部分到货不会算齐套**：`gap>0` 的判断在状态判断之前，`required=10, arrived=4, in_stock=2` 的行 gap=8，进缺料且 `statusLabel=到货`（测试 M-ARRIVED、K-SHORT 均覆盖）。
- **无需求行返回 null**：`_kitting_rate` 在 `total==0` 时返回 `None`（main.py:5403-5406）；项目与单机台都走这条。真实库 TEST-3D-01 / TEST-20261009-001（0 行）返回 `kittingRate=null`，导出写 `""`，模板写 `—`，没有拿 0 冒充。
- **不可被技巧性抬高**：DB 的 `CHECK(required_quantity > 0)` 堵住了「零需求行刷齐套」；没有「只看状态不看缺口」的快捷路径；`round(...,1)` 也不改分母。**但**分母排除了 `unmapped` 行（P2-8②），以及 P1-2 的反向问题——当前口径只会压低、不会抬高齐套率。
- **结论**：防虚高的目标达成；但 `in_stock` 单口径把「已到货待入库」误判为缺料（P1-2），需要产品定口径。

### 2. 跨机台合并：求和正确，不会互相抵消；「最不利状态」规则正确
- **求和还是取最大**：`required/arrived/inStock/shortage` 全部 `+=`（main.py:5526-5529）。关键是**先按行算 gap 再求和**：某机台 `in_stock` 富余时该行 gap=0、根本不进 `short_rows`，不会抵消另一台机台的缺口（不会出现 `max(0, Σrequired − ΣinStock)` 的净额抵消）。反过来也保守：Σ每行缺口 ≥ 净额缺口。
- **不会把「A 有库存、B 无库存」算成有库存**：缺口按行独立；合并后的 `affectedDeviceNos` 只包含该料号**有缺口**的机台（`_devices` 只从 short_rows 收集，5519-5520），有库存的机台不出现在影响清单里。
- **最不利状态**：任一缺料行 `OUT_OF_STOCK` → `OUT_OF_STOCK`；否则任一 `ARRIVED` → `ARRIVED`；否则 `IN_STOCK`（5542-5550），与文档一致。唯一尴尬是最后一档在缺料清单里显示「在库」（P2-6）。
- **排序/机台顺序**：机台按 `(sequence_no, device_no)`（5546-5548），项目顺序稳定；合并键是料号（`materials.code` 有唯一约束，真实库 0 个大小写重复）。
- **小瑕疵**：合并后的 `requiredQuantity/inStockQuantity` 只统计缺料行（P2-5），不是该料号项目总量。

### 3. 权限一致性：确实复用同一套函数；ASSEMBLER 403 有效；仓库差异属需求明示、但需产品签字
- **复用而非拷贝**：`_kitting_authorize` 只有 4 行，非仓库角色直接调 `_pmr_authorize`（main.py:5391-5395）；设备可见性走 `_pmr_project_devices`（5572）、机台名走 `_pmr_device_names`（5576）、项目解析走 `_pmr_resolve_project`；三个 API 端点都在解析项目**之前**鉴权（5656、5684、5786），不泄露项目是否存在。
- **ASSEMBLER 越权 403**：项目有设备但本人一台都没参与 → `403 PROJECT_FORBIDDEN`；指定他人机台 → `403 FORBIDDEN`（main.py:4813-4829）；测试 `test_assembler_scope_and_foreign_project_403`（tests/test_kitting_shortage.py:347-380）同时覆盖列表/概览/导出，断言响应里没有 `SECRET-1`、合并行的 `deviceNoText` 里没有 `P2`。导出同样 403。
- **WAREHOUSE_ADMIN 差异**：`_pmr_authorize`（4751）只放行 ADMIN/主管/计划员/ASSEMBLER，需求 1 的 `/material-requirements` 对仓库 403 保持不变（tests/test_kitting_shortage.py:391-393 锁住）。需求 2 第 4 条明写「WAREHOUSE_ADMIN 可查」，实现只在 `_kitting_authorize` 加例外。**判断**：这是需求冲突下的合理取舍（仓库确实要催料清单），且是只读、无写接口；但它让仓库看到所有项目的机台/料号/缺口，建议产品书面确认。代码层面没有第二套 ACL。
- **`unmappedRequirementCount` 对装配工隐藏有效**：显式置 `None`（5626-5627），装配工无法从该字段推断项目级需求规模；但同一响应里的 `projectDeviceCount` 泄露总机台数（P2-3①），建议一并处理。

### 4. xlsx_writer 重构：单 sheet 无回归（逐 part 等价），多 sheet 结构正确
- **单 sheet 等价性实测**：把 `76d1965` 的旧模块与 `bb27f14` 的新模块同时载入，对 4 组输入（中文/控制字符/空表/超长名/sheet_name 覆盖）分别调用 `build_xlsx`：`namelist` 相同、**7 个 part 逐字节相同**、zip 字节也相同（同一秒内）。`build_xlsx` 只是拼一个 dict 委托给 `build_xlsx_workbook`（227-247），`_sheet_xml` 的逻辑原样搬移，`_sheet_name` 仍在 `_unique_sheet_names` 里执行。

- **需求 1 回归**：`tests/test_project_material_requirements.py -k export` 3 passed（列/层级/小计合计/控制字符）；`test_admin_web_nav.py + test_admin_web_exports.py` 8 passed。`_CONTENT_TYPES`/`_WORKBOOK_RELS` 常量已删但无其他引用（grep 全仓仅 xlsx_writer 自身）。

### 5. SQL 安全：通过
- 新增查询全部参数绑定：`_kitting_requirement_rows`（5416-5431）、`_kitting_dataset` 的 `project_device_count`（5573-5575）、`unmappedRequirementCount`（5620-5625）。
- 动态拼接只有 `IN ({marks})`，占位符数量由 `len(device_ids)` 生成，无用户输入；`ORDER BY d.sequence_no, m.code` 是常量。
- 新增代码没有 `LIKE`：`material_code` 过滤在 Python 侧做 `wanted in code.upper()`（5501-5504），不拼 SQL，因此无转义问题（代价是内存扫描）；项目模糊搜索复用的 `_pmr_like` 已有转义。
- 排序在 Python 侧，无注入面。

### 6. 分页/性能：内存切片，万级可用；排序稳定，total 一致
- `page_items = items[start:start+page_size]`（5703-5704），`total = len(items)`（5699），`hasMore = start+len(page_items) < total`（5711），越界页空列表 + total 不变。默认 50/最大 200 由 `Query` 约束（5679-5680）。
- **排序稳定**：`(-shortage, -affectedDeviceCount, materialCode)`，第三键是合并后的唯一料号，构成全序；即使 Python 稳定排序也不依赖插入顺序，翻页不重不漏（5557-5558）。测试用 5 条、pageSize=2 翻 3 页验证。
- **性能实测**：26B-012（20,552 需求行 / 118 机台 / 2,750 合并料号）单次 `_kitting_dataset` 0.59s；万级可行，10 万行约 6s。问题是三个接口都全量构建（概览连 `items` 都建完再丢，5629/5669），每个分页/过滤都重算，没有 SQL 聚合或缓存（P2-4）。

### 7. 不造假：行级全部满足；「已到货」是唯一例外
- 缺口为 0 不出现：`short_rows` 只收 `gap>0`（5458-5478），M-ZERO、M-FULL 在测试里断言不出现在响应/导出。
- 无需求记录不出现：清单只由 `order_material_requirements` JOIN `materials` 生成，M-NOREC（只在主档）不出现（tests/test_kitting_shortage.py:298-300）。
- 无需求行 `kittingRate=null`：5403-5406，真实库两个空项目验证；导出 `""`、页面 `—`，没有把 null 当 0 汇总。
